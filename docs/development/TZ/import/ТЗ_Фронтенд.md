# ТЗ на фронтенд сервиса управленческой таблицы «Факт»

**Проект:** ТПК БРИК, сервис автоматического формирования блока «Факт» по заказам из 1С
**Адресат документа:** разработчик (агент), реализующий веб-интерфейс
**Редакция:** 1.0 от 16.08.2026
**Смежные документы:** [ТЗ на сервис](../ТЗ.md), [постановка и устройство расчёта](../development/HANDOFF.md)

> Документ описывает **продуктовые требования**: что пользователь должен уметь сделать,
> из каких данных это собирается и как система обязана себя вести. Дизайн, вёрстка,
> выбор фреймворка и компонентной базы в объём документа **не входят** и остаются
> на усмотрение исполнителя.

---

## 1. Зачем этот интерфейс

Бэкенд уже считает управленческую таблицу «Факт» по заказам: забирает проводки из 1С,
раскладывает затраты по колонкам, распределяет общехозяйственные расходы и отдаёт
готовый `.xlsx`. Сегодня им пользуются через Swagger — это работает для разработчика
и не работает для экономиста.

**Цель фронтенда:** дать сотруднику заказчика (экономист, бухгалтер) выполнить
месячный цикл целиком, не открывая консоль и не читая JSON:

1. посмотреть, что попадёт в расчёт за месяц, **до** того как его запускать;
2. запустить расчёт и дождаться результата, понимая, что происходит;
3. увидеть результат на экране, а не только в скачанном файле;
4. получить внятное объяснение, если расчёт не сошёлся или 1С недоступна;
5. скачать `.xlsx` для переноса колонок в рабочую таблицу менеджеров.

**Метрика успеха:** экономист закрывает месяц без участия разработчика и без Swagger.

## 2. Пользователи

| Роль | Кто это | Что делает в интерфейсе |
|---|---|---|
| **Экономист** (основной пользователь) | Сотрудник заказчика, готовит блок «Факт» ежемесячно | Весь цикл раздела 1. Знает бухгалтерию, не знает HTTP |
| **Разработчик/сопровождение** | Исполнитель | Диагностика: почему не сошлось, что вернула 1С, состав заказов |

Разделения прав нет: пользователи внутри локальной сети заказчика, авторизация
на текущем этапе не реализуется (см. 10.3).

## 3. Глоссарий

Термины обязаны использоваться в интерфейсе **в том же виде**, в каком они звучат
у заказчика. Переименовывать «под красоту» нельзя: пользователь сверяет цифры
с ОСВ из 1С и с рабочей таблицей менеджеров.

| Термин | Значение |
|---|---|
| **Заказ** | Единица учёта. В 1С — номенклатурная группа, номер заказа зашит в её наименование (`П3747 (изделие…)` → заказ `П3747`) |
| **CC** | Материалы, комплектующие, услуги сторонних организаций, командировочные |
| **CD** | ЗП производственных рабочих и страховые взносы |
| **CE** | Накладные расходы общепроизводственные (25 сч) |
| **CF** | Накладные расходы общехозяйственные (26 сч), распределяются между заказами |
| **Брак (28 сч)** | Потери от брака. Отдельная колонка, **в себестоимость по данным 1С не входит** |
| **Себестоимость по 1С** | CC + CD + CE. Обязана совпадать с оборотом Дт 20.01 |
| **Полная упр. себестоимость** | CC + CD + CE + Брак + CF |
| **НЗП** | Незавершённое производство: дебетовый остаток по 20.01 на конец месяца |
| **Заказ в работе** | Есть положительный остаток НЗП. Признак **справочный** |
| **База распределения** | Прямая ЗП производственных рабочих без взносов. По ней делится 26 счёт |
| **Сходимость (сверка)** | Обязательные контроли. Не сошлось — отчёт не выдаётся |

⚠️ Частая ошибка при отображении: «в работе» и «участвует в распределении 26 сч» —
**разные признаки**. Заказ, закрывшийся в расчётном месяце, в работе не находится,
но накладные расходы месяца делит наравне с остальными. Интерфейс не должен
их смешивать и не должен подсказывать, что один следует из другого.

## 4. Границы работ

### 4.1. Входит

1. Веб-интерфейс поверх существующего HTTP API сервиса (раздел 5).
2. Сценарии раздела 6 целиком.
3. Обработка всех состояний из раздела 8, включая долгий расчёт и отказ по сходимости.
4. Русскоязычный интерфейс.

### 4.2. Не входит

1. **Любая запись в 1С.** Сервис работает только на чтение, интерфейс не предлагает
   пользователю ничего, что выглядело бы как правка учётных данных.
2. **Редактирование рабочей таблицы менеджеров** «Управленка новая». Перенос колонок
   в неё делает заказчик вручную, по номеру заказа.
3. **Пересчёт методологии на клиенте.** Все суммы приходят с бэкенда посчитанными.
   Фронтенд не складывает CC+CD+CE сам и не пересчитывает проценты распределения:
   расхождение клиентской арифметики с серверной обесценивает отчёт.
4. Плановый блок таблицы, расчёт нормо-часа, ценообразование.
5. Мобильная версия (рабочее место — десктоп).

## 5. Контракт с бэкендом

Базовый URL сервиса задаётся конфигурацией сборки (переменная окружения), в код
не зашивается. Все методы префиксованы `/api/v1/table-creator`.
Формат ответа — JSON, документация живая: `/docs` (Swagger) и `/openapi.json`.

### 5.1. Реализовано сейчас

#### `GET /api/v1/table-creator/orders?date=<период>`

Состав заказов периода **без запуска расчёта**. Отвечает за секунды.

Ответ:

```json
{
  "period": "2026-06",
  "orders": [
    {
      "order_key": "b0f1…",           // GUID номенклатурной группы
      "order_name": "П3747 (изделие, 2 шт_Заказчик)",
      "order_code": "П3747",          // номер заказа = ключ связи с таблицей менеджеров
      "turnover": "11124347.86",      // оборот Дт по счетам расчёта (20.01 и 28)
      "wip_balance": "3402881.15",    // остаток НЗП на конец периода
      "in_progress": true,            // справочный признак «в работе»
      "in_report": true               // попадёт ли заказ в расчёт
    }
  ],
  "orders_filter": null,              // действующий фильтр состава; null — берутся все с оборотом
  "turnover_without_order": "0.00",   // оборот без номенклатурной группы — ни в один заказ не попадёт
  "total": 27,
  "in_report_count": 27,
  "in_progress_count": 19,
  "total_turnover": "42812784.23",
  "unmatched": []                     // GUID групп, у которых не удалось определить номер заказа
}
```

Заказы приходят отсортированными по убыванию оборота.

#### `POST /api/v1/table-creator/report?date=<период>`

Полный расчёт месяца. Возвращает файл `.xlsx`
(`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`),
имя файла — в заголовке `Content-Disposition`, вида `Факт_управленка_2026-06.xlsx`.

⚠️ **Метод долгий: минуты, а не секунды** (см. 7.1). Тело запроса не передаётся,
период идёт в query-параметре.

Книга содержит четыре листа: «Свод по заказам», «Распределение 26 сч», «Расшифровка»,
«Счёт 26 (период)». Формулы в ней **живые**: заказчик правит сумму 26 счёта или снимает
признак участия и видит пересчёт. Интерфейс это свойство файла не ломает и не дублирует.

#### Служебные

`GET /health` → `{"status": "Ok"}`. Используется для индикации доступности сервиса.

### 5.2. Требуется от бэкенда (реализуется параллельно)

Эти методы **ещё не готовы**. Интерфейс проектируется под них сразу, разработка
ведётся на моках, соответствующих контракту ниже; при появлении реальных ручек
подмена мока не должна требовать переписывания экранов.

| Метод | Назначение | Что вернёт |
|---|---|---|
| `GET /report?date=…` | Результат расчёта в JSON — источник данных для экрана отчёта | Свод по заказам, распределение 26 сч, расшифровка по статьям, итоги, результаты сверок |
| `POST /report` с телом | Расчёт с ручным переопределением участия заказов в распределении 26 сч | То же + признак, что применялось переопределение |
| Фоновый режим: `task_id` + опрос статуса | Расчёт перестаёт быть одним долгим HTTP-запросом | `{task_id, status, progress?, result?}` |
| Кэш закрытых периодов | Повторный запрос месяца отдаётся мгновенно | Признак «из кэша» и время исходного расчёта |

Структура JSON-отчёта (ориентир — доменные модели бэкенда, поля уже существуют):

```json
{
  "period": "2026-06",
  "orders": [
    {
      "order_code": "П3747",
      "order_name": "П3747 (изделие…)",
      "by_column": {"CC": "7015883.49", "CD": "1151502.95", "CE": "2956961.42", "28сч": "0.00"},
      "by_article": {"20. ЗП производственных рабочих": "910277.17"},
      "direct_wage": "910277.17",
      "overhead_26": "4651595.18",
      "wip_balance": "…",
      "in_progress": true,
      "cost_1c": "11124347.86",
      "defects": "0.00",
      "full_cost": "15775943.04"
    }
  ],
  "overhead_26_total": "5639903.92",
  "articles_26": {"26. Аренда": "…"},
  "allocation_base": "1103680.69",
  "unmapped_orders": [],
  "total_cost_1c": "15124465.77",
  "total_defects": "0.00",
  "total_full_cost": "20764369.69"
}
```

**Фронтенд обязан быть терпим к составу колонок.** Набор целевых колонок в `by_column`
будет расширяться: по 44 счёту (коммерческие расходы) и по способу переноса брака
решение заказчика ещё не получено, колонка «БГ» (банковские гарантии) тоже открыта.
Таблицы строятся **по фактическому составу ключей**, а не по захардкоженному списку
`CC/CD/CE`. Порядок и человекочитаемые названия колонок берутся из словаря
соответствий, который правится в одном месте.

### 5.3. Форматы данных — обязательные правила

1. **Все денежные суммы приходят строками** (`"11124347.86"`), это не ошибка сериализации,
   а требование точности: суммы сверяются с бухгалтерией до копейки.
   **Запрещено** прогонять их через `parseFloat`/`Number` для отображения, сортировки
   или суммирования. Отображение — форматирование строки; сортировка и любые сравнения —
   через decimal-совместимое сравнение (библиотека произвольной точности либо сравнение
   целых копеек). Двоичная погрешность в этом продукте — дефект, а не мелочь.
2. **Формат вывода сумм:** разделитель разрядов — неразрывный пробел, десятичный —
   запятая, всегда две цифры после запятой: `15 124 465,77`. Ноль показывается как
   `0,00`, а не пустой ячейкой: пустая ячейка читается как «нет данных», а ноль —
   это ноль.
3. **Период** пользователь вводит **в свободной человеческой записи**. Принимаются
   `2026-06`, `06.2026`, `6/2026`, `июнь 2026`, `июня 2026`, `June 2026`.
   Двузначный год отвергается намеренно. **Разбор периода — обязанность бэкенда**:
   фронтенд не дублирует правила регулярными выражениями, а отправляет введённое
   и показывает сообщение сервера при отказе. Допускается вспомогательный выбор
   месяца/года, но ручной ввод обязан остаться.
4. **Ключ заказа для человека — `order_code`** (`П3747`), именно по нему идёт перенос
   в таблицу менеджеров. `order_key` (GUID) в интерфейсе не показывается никогда,
   кроме диагностического блока для несопоставленных групп.

## 6. Пользовательские сценарии

### С1. Предпросмотр состава расчёта

**Зачем:** заметить проблему в исходных данных до расчёта, а не по расхождению в итогах.

1. Пользователь указывает период.
2. Интерфейс запрашивает состав заказов и показывает таблицу: номер заказа,
   наименование группы, оборот, остаток НЗП, «в работе», «попадёт в расчёт».
3. Показываются сводные счётчики: всего групп, попадёт в расчёт, из них в работе,
   суммарный оборот.
4. **Отдельно и заметно** показываются два признака неблагополучия:
   - `unmatched` — группы, у которых не удалось определить номер заказа.
     Пояснение пользователю: расчёт по ним не сойдётся, нужно поправить наименование
     номенклатурной группы в 1С;
   - `turnover_without_order` ≠ 0 — оборот без номенклатурной группы, он не попадёт
     ни в один заказ.
5. Если действует фильтр состава (`orders_filter` не `null`) — это показывается явно:
   пользователь должен понимать, что видит не все заказы периода.

Требования: таблица сортируется по любой колонке, ищется по номеру заказа
и по наименованию, состав видно целиком без постраничной навигации
(порядок величин — десятки строк).

### С2. Запуск расчёта и получение файла

1. С экрана предпросмотра пользователь запускает расчёт того же периода —
   повторно вводить период не требуется.
2. Пока расчёт идёт, интерфейс обязан:
   - показывать, что операция выполняется, и **предупреждать о длительности**:
     обычно секунды, но первый запрос после простоя 1С добавляет до полутора минут;
   - не давать запустить второй расчёт того же периода параллельно;
   - не «отваливаться» по клиентскому таймауту раньше сервера (см. 7.1);
   - позволять уйти с экрана и вернуться, не потеряв запущенную операцию
     (после появления фонового режима — обязательно; до него — предупреждать,
     что уход со страницы прервёт запрос).
3. По завершении: файл сохраняется пользователю, имя берётся из `Content-Disposition`.
4. Результат расчёта остаётся доступен на экране (см. С3), а не исчезает вместе
   со скачанным файлом.

### С3. Просмотр результата на экране

Доступен после появления JSON-метода (5.2). Три представления одних и тех же данных:

**Свод по заказам** — строка на заказ: номер, CC, CD, CE, брак, CF,
себестоимость по 1С, полная управленческая себестоимость. Строка итогов обязательна
и всегда видна. Клик по заказу раскрывает его расшифровку по статьям.

**Распределение 26 счёта** — прямая ЗП, остаток НЗП (справочно), участие в распределении,
доля в процентах, сумма CF. Отдельно и заметно: общая сумма 26 счёта за период
и база распределения. Сумма долей обязана показываться и равняться 100 %.

**Расшифровка** — построчно: заказ, статья затрат, счёт учёта, сумма, целевая колонка.
Фильтруется по заказу, по колонке и по счёту, ищется по наименованию статьи.
Это инструмент проверки: пользователь приходит сюда с вопросом «почему в CE такая сумма».

Дополнительно: расшифровка 26 счёта по статьям (`articles_26`) отдельным блоком.

### С4. Отказ по несходимости

**Это штатный, а не аварийный сценарий**, и интерфейс обязан подать его именно так.
Сервис сознательно не выдаёт отчёт, который не сошёлся с 1С.

При `422` с ошибкой сверки:
- показать, что расчёт выполнен, но **результат не выдан, потому что не сошёлся**;
- перечислить не сошедшиеся проверки: название проверки, ожидалось, получено,
  расхождение (бэкенд отдаёт их построчно в тексте ошибки; после появления
  структурированного ответа — списком);
- дать понятную следующую шаг: посмотреть состав заказов (С1), обратиться
  к сопровождению, повторить расчёт;
- **не предлагать «скачать всё равно»**. Такой кнопки быть не должно.

### С5. Ручное переопределение участия в распределении

Доступен после появления соответствующего метода (5.2).

Экономист снимает у отдельных заказов участие в распределении 26 счёта и запускает
пересчёт. Требования:
- видно, какие заказы переопределены вручную и чем это отличается от расчётного признака;
- видно, как изменились доли и суммы CF (было/стало);
- переопределение сбрасывается одним действием;
- переопределение **не сохраняется молча** между периодами: новый период —
  чистый расчётный признак.

⚠️ Продуктовое ограничение: в выгруженном `.xlsx` признак участия по умолчанию задан
формулой от прямой ЗП. Если пользователь переопределил участие в интерфейсе, файл
обязан отражать именно переопределённое состояние — иначе Excel пересчитает по-своему
и разойдётся с тем, что человек видел на экране. Это требование к бэкенду,
фронтенд обязан показать пользователю, какое состояние ушло в файл.

### С6. История расчётов

Список выполненных расчётов: период, когда посчитан, результат (успех / не сошлось /
ошибка 1С), длительность, ссылка на повторное скачивание. Источник — бэкенд
(журнал расчётов и кэш закрытых периодов). Пользователь должен видеть, что период
за месяц уже считался и чем закончился.

Если период отдан из кэша — это показывается явно, с датой исходного расчёта
и возможностью запросить принудительный пересчёт.

## 7. Поведение при долгих операциях

### 7.1. Длительность — свойство 1С, а не сервиса

| Операция | Норма | Худший случай |
|---|---|---|
| Состав заказов (`GET /orders`) | ~2 с | до полутора минут на «холодной» базе |
| Полный расчёт (`POST /report`) | ~5 с на «тёплой» базе | **до 15 минут** |

Первый запрос к 1С после простоя стоит ~80 секунд независимо от тяжести запроса.
Предсказать, тёплая база или нет, клиент не может.

Требования:

1. Клиентский таймаут на расчёт — **не меньше 15 минут** либо отсутствует вовсе.
   Оборвать запрос раньше сервера — значит потерять уже выполненную работу.
2. Индикация выполнения обязательна с первой секунды. Если операция идёт дольше
   ~10 секунд, пользователю сообщается, что это нормально и почему.
3. Никаких «автоматических повторов» долгого расчёта силами фронтенда: каждый
   повтор — это ещё один сеанс в 1С. Повтор только по явному действию пользователя.
4. Параллельно к сервису идёт **не более одного тяжёлого запроса**: 1С работает
   в один поток соединений. Интерфейс не должен фоново опрашивать `/orders`
   во время идущего расчёта.

## 8. Ошибки и состояния

Сообщения сервера безопасны для показа: ни паролей, ни заголовков в них не попадает.
Текст сервера показывается пользователю, но **не вместо** человеческого объяснения.

| Код | Причина | Что показать |
|---|---|---|
| `400` | Период не разобран: неизвестное слово, двузначный год, месяц `13` | Ошибка ввода периода рядом с полем + перечень принимаемых форматов из ответа |
| `422` | Не передан `date`, лишний параметр, **или расчёт не сошёлся**, или счёт отсутствует в плане счетов | Различать: ошибка ввода и отказ по сходимости (С4) — это разные экраны |
| `500` | Не настроено подключение к 1С либо не удалось сохранить файл | Проблема на стороне сервиса, обратиться к сопровождению. Пользователь ничего не исправит сам |
| `502` | 1С ответила ошибкой или нечитаемым телом | Учётная система вернула ошибку, повторить позже |
| `504` | 1С не ответила за отведённое время | Учётная система не отвечает, повторить позже. Явно сказать, что расчёт **не выполнен**, данные не пострадали |
| Сеть/сервис недоступен | Бэкенд не поднят | Сервис недоступен, проверить доступность (использовать `/health`) |

Общие правила:

1. Формулировки на русском, без англоязычных технических терминов и без стектрейсов
   в основном тексте. Технические детали — в раскрываемом блоке «подробности».
2. Каждая ошибка сопровождается **действием**: повторить, посмотреть состав, скопировать
   текст ошибки для сопровождения.
3. Пустые состояния описываются содержательно: «за июнь 2026 в 1С нет ни одной группы
   с оборотом» — это не то же самое, что ошибка.
4. Ошибка одной операции не ломает экран целиком: пользователь остаётся в контексте
   и может продолжить.

## 9. Требования к содержанию экранов

Состав, не оформление. Разбиение на страницы/панели — на усмотрение исполнителя.

**Обязательно присутствует:**

1. **Выбор периода** — единая точка входа, доступна с любого экрана; текущий выбранный
   период виден всегда.
2. **Состав заказов** (С1) — таблица + счётчики + блок предупреждений.
3. **Запуск расчёта и его состояние** (С2) — включая предупреждение о длительности.
4. **Результат расчёта** (С3) — свод, распределение 26 счёта, расшифровка,
   расшифровка 26 счёта.
5. **Скачивание `.xlsx`** — доступно и сразу после расчёта, и из истории.
6. **История расчётов** (С6).
7. **Состояние сервиса** — доступность бэкенда, действующий фильтр состава заказов
   (`orders_filter`), если он задан.

**Требования к любой таблице сумм:**

- строка итогов не скрывается за прокруткой;
- шапка фиксируется при прокрутке — таблица широкая, номер заказа обязан оставаться
  на виду;
- выгрузка видимой таблицы в CSV/буфер обмена — полезна, но не обязательна;
- ширина не приводит к горизонтальной прокрутке всей страницы: прокручивается сама
  таблица.

## 10. Нефункциональные требования

### 10.1. Окружение

Рабочее место — десктоп, актуальный Chrome/Edge. Сервис и интерфейс работают
во внутренней сети заказчика; интернет может отсутствовать, поэтому **внешние CDN
недопустимы**: шрифты, скрипты и стили поставляются вместе со сборкой.

### 10.2. Конфигурация

Адрес API задаётся при сборке/развёртывании переменной окружения. Хардкод адреса
в исходниках — дефект. Сервис отдаёт CORS с разрешёнными источниками, отдельная
настройка на фронте не нужна.

### 10.3. Безопасность

Авторизации на текущем этапе нет — доступ ограничивается сетевым контуром заказчика.
Интерфейс **не хранит** ни реквизитов 1С, ни каких-либо секретов: он их не получает
и получать не должен. Требование появления авторизации возможно на следующем этапе,
поэтому точка входа в приложение проектируется так, чтобы её можно было закрыть
экраном входа без переработки навигации.

### 10.4. Язык

Интерфейс русскоязычный. Многоязычность не требуется. Бухгалтерская терминология —
строго из раздела 3.

## 11. Критерии приёмки

Проверяется на контрольном периоде **июнь 2026**.

1. Период вводится всеми поддерживаемыми способами (`2026-06`, `06.2026`, `июнь 2026`,
   `June 2026`) и даёт один и тот же результат; `06.26` и `2026-13` отклоняются
   с понятным сообщением.
2. Состав заказов за июнь 2026 отображается полностью и совпадает с ответом API:
   27 групп, суммарный оборот 42 812 784,23.
3. Расчёт запускается с экрана, отрабатывает без клиентского таймаута, файл
   скачивается с именем `Факт_управленка_2026-06.xlsx`.
4. Суммы на экране совпадают с содержимым выгруженного файла **до копейки**;
   контрольные значения: себестоимость по 1С 15 124 465,77 по четырём эталонным
   заказам, оборот 26 счёта 5 639 903,92.
5. Ни одна сумма в интерфейсе не искажена округлением: значение с копейками
   отображается с копейками, итоги совпадают с серверными.
6. Искусственно внесённое расхождение (тестовый стенд) приводит к экрану «расчёт
   не сошёлся» с перечнем проверок, кнопки принудительного скачивания нет.
7. При остановленном бэкенде и при недоступной 1С показываются разные, корректные
   по смыслу сообщения; интерфейс не «висит» молча.
8. Группа с непарсящимся наименованием (`unmatched`) видна в предпросмотре как
   предупреждение.
9. Появление в ответе новой целевой колонки (например, 44 счёт) не ломает таблицы:
   колонка отображается без правки кода таблиц.

## 12. Открытые вопросы

Ответы влияют на состав экранов; до их получения интерфейс реализуется так, чтобы
изменение не требовало переработки.

1. **Фоновый режим расчёта.** До появления `task_id` расчёт живёт в одном HTTP-запросе,
   и уход со страницы его прерывает. Нужно подтвердить, что на первом этапе это
   приемлемо.
2. **Состав заказов отчёта.** Главный методологический вопрос заказчика (см. ТЗ п. 9.1):
   эталонный файл построен по 4 заказам, в базе за июнь их 27. Если появится
   пользовательский выбор состава — это отдельный экран, сейчас он не проектируется;
   действующий фильтр задаётся настройкой сервиса и показывается только на чтение.
3. **Счёт 44 (коммерческие расходы) и брак (28 сч).** Способ отображения и переноса
   в таблицу менеджеров заказчиком не утверждён. Требование к фронтенду одно:
   колонки берутся из данных, а не из кода (5.2).
4. **История расчётов** зависит от журнала на бэкенде: нужно согласовать, хранится ли
   она между перезапусками сервиса.
